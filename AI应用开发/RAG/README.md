# 1. RAG的流程

RAG主要分为三个部分。

1. 索引。LLM在使用前，需要将所有知识都存储起来，方便以后调用。
   * 数据解析与清洗。首先读取所有源文件，如PDF、网页、Word等，提取出纯文档，去除无关字符。
   * 文本分块。将长文档按照分块算法切分成语义完整的多个段落。常见的策略有固定长度分块、按符号分块、父子分块等。
   * 向量化。将分块使用嵌入模型转换为高维向量。
   * 构建向量索引。将生成的向量和原始文本存入向量数据库。
2. 检索。上面存储了数据后，用户输入了问题，需要能够在数据库中检索相关的文档。
   * 查询向量化。将用户的问题通过同一个嵌入模型转换成向量。
   * 相似度匹配。在向量数据库中通过近似最近邻搜索，计算查询向量与所有文档的余弦相似度，召回前N个最相似的文档。
   * 重排序。第一次召回的文档知识根据向量距离计算排名，可能不准确。重排序会使用交叉编码器对召回的文档重新排序，过滤掉相似度低于阈值的无关文档，选取最相关的K个文档。
3. 增强。将检索到的文档放到提示词。
   * 提示词增强。将检索到的文档作为参考资料插入到提示词，与原始问题拼接形成完整的提示词。如”基于一下参考资料回答问题“等。
   * 大模型推理。根据提示词，大模型能够生成更准确的答案。
   * 标注引用。由于LLM能够知道知识来源于哪个文档，因此生成时，可以标上引用，能够让用户进行验证。

# 2. Embedding是什么，1526维是什么

Embedding就是嵌入，将文本转化成向量。1536维就是用1536维的向量来表示一段文本。通过余弦相似度能够计算两个向量有多接近。

# 3. 怎么设计企业级知识库问答系统

知识库问答需要使用RAG。将企业的所有知识文档都存储到向量数据库，这样回答的时候就能自动检索相关知识了。

首先的话需要进行数据清洗和切片。将各种类型的数据都转化为纯文本，通过父子切块来将文本切块，然后通过嵌入模型转化成向量。这里的分块可以添加元数据，如文件名、页码等信息，能够在检索时进行过滤。

然后就是数据存储。转换成向量之后，需要进行存储。通常需要将分块存储到向量数据库，将文档存储到关系型数据库中。

然后是RAG。用来进行查询改写、多路召回、重排序、上下文增强和调用大模型生成答案等。

还需要对外提供API接口，给前端应用或者其他服务对外提供问答功能。

这样可以使用RAGAS来进行测试，可以监控问答系统的忠诚度、相关度、精确度和召回率等指标。

# 4. Chunk大小怎么选择

如果分块过小，虽然能够精确匹配，但是语义不完整。如果过大，虽然语意完整，但是检索不精确，文档中只有小部分与问题相关。

一般来说，分块选择512token或者1024token就可以了。

此外，为了避免语义被切割，需要使用父子分块、重叠分块、语义切分等方法来分块。如父子分块需要给相邻的块进行分组，如果子块被检索，那么整一组的块都需要被选择。还有重叠分块，在切分的边界上额外向外延伸10%左右，避免在边界上切割语义。语义切分就是让小模型来自主切分文本。

# 5. 召回率差怎么解决

召回率差，说明当前的问题与向量库的相关文本相关性比较低。

1. 知识库没有内容。如果知识库根本没有当前问题需要的答案，那么自然召回率差。
2. 知识库质量差。如果其他类型的文本通过OCR扫描成纯文本的时候出现乱码、空格等情况，会导致embedding的语义被破坏。
3. 切块问题。如果切块太小，那么语义容易被切割导致检索不出来。如果切片太大，embedding会将语义平均话，导致检索时相似度不够。
4. embedding模型不好。如果模型质量很差，或者文本为中文，选择了只支持英文的模型，会出现向量不能表示语义的情况。
5. embedding模型专业性不足。如果需要面向专业性的文本，模型可能无法区分专业术语。那么就需要微调。
6. 然后就是输入的问题。如果用户输入质量差，如这个错了，你改一下之类，会导致输入与文档相似度低。
7. Top-K不合理。如果K过小，可能只包含少部分相关的文档，大部分都没有被选择。
8. 没有重排序。如果不进行重排序，那么给出来的文档就是都是相关的，模型都需要仔细看。而如果经过重排序，就能找出最相关的文档，重新进行排序。这样，第一个文档可能就是最重要的，模型能够快速获取。

可以构建评估数据集，包含问答对，以及应当检索到的文档ID。将数据集放入RAG，计算是否召回了应当检索到的文档ID。能够计算出召回率。如果召回率过低，可以有很多方法来提升。

1. 查询改写。让LLM将查询改写成多个版本，用这几个版本一起查询，最终合并结果并返回。
2. HyDE假设性文档嵌入。让LLM先给出假定答案，使用假定答案进行检索。
3. 优化分块算法。可以使用父子分块，这样检索到子块时，能够将子块相关的一并查询出来，避免查找不准的情况。
4. 优化Embedding。有可能知识比较专业，通用的Embedding模型对专业术语不敏感。这样就需要对Embedding使用企业问答对进行微调。
5. 混合检索。通过向量检索查找语义相关的，通过关键词检索进行关键词匹配，将两者的结果按权重进行加权求和，得到最终结果。
6. 重排序。第一次召回时可以召回多个结果，然后经过重排序时，选取前K个与问题最相关的分块并返回。

# 6. 如何降低RAG成本

LLM最大的成本在于提示词过长。因此，可以在RAG检索完成后压缩提示词，使用LLMlingua等技术，将长提示词压缩至20%，这样能够降低输入成本。

还有可以进行语义缓存。将先前的问题和答案进行缓存，如果后续的问题语义与先前的问题相关，那么可以直接返回这个答案，不调用LLM。

优化模型。前端展示的是简单的小模型，简单的问题都通过小模型来解决。如果遇到复杂问题，才调用大模型来解决。

优化检索，将RAG检索的K值减少，通过ReRank来提高精度。减少提示词长度。

# 7. 什么是查询改写，如何提高检索效果

用户的提问通常基于上下文来问的。如”它多少钱“、”这怎么实现“等，都是需要查看上下文来获取完整信息的。那么Query改写就是对用户的原始问题进行优化，使得更适合检索。如用户先前问题是”什么是RAG“、”如何实现它“，那么Query改写就会改写为”如何实现RAG检索增强生成系统“。

此外，Query改写也能进行查询拓展。如查询为”Python多线程“，那么改写后会变为`"""Python多线程 Python threading模块 Python GIL全局解释器锁`等。将这些改写后的多个句子一起检索，通过重排序给出最相关的多个回答，能够尽可能地覆盖与查询相关的所有语义。

还有，Query改写也用在HyDE中。因为检索时，问题与答案之间的相似度不一定高。所以可以先让LLM生成一个假设性答案，再根据这个假设性答案来进行检索。

最后，Query改写用在多查询生成。用户的问题可能是一个抽象复杂的问题。这时需要LLM对复杂问题进行拆解，生成多个方面的小问题，针对小问题来进行检索。这样能够提高检索的召回率。

# 8. 什么是上下文压缩

上下文压缩是从检索结果中提取最相关的片段，降低Token输入。如果检索到很多相关文档，直接输入到模型，可能只有其中的一般被使用，另外的只能占用空间。

1. 基于LLM的提取。让LLM查看检索的文档，让它只保留与问题相关的句子。
2. Rerank。先第一次召回文档，然后进行交叉编码重排序，只保留Top-K个最相关文档。
3. 压缩。将很长的上下文压缩成摘要，能够很大程度减少上下文数量。

# 9. Embedding如何选择

Embedding有很多需要考虑的方面。如语言，看是否支持多语言，成本，看使用闭源还是开源，性能，看检索任务的指标，维度，数据量越大，维度应该越高。

闭源的API模型有text-embedding-3-large，虽然性能好，但是价格昂贵，且数据会被收集。还有text-embedding-3-small，性能略低，但便宜。

开源的有bge-large-zh-v1.5，支持中文，性能较好。beg-large-en-v1.5支持英文，性能也好。还有BGE-M3，支持多语言，性能非常好。

中文应使用bge-large-zh-v1.5，英文使用bge-large-en-v1.5。

# 10. GraphRAG是什么

GraphRAG是知识图谱＋RAG。

RAG虽然能够通过向量相似度检索相关内容，但对跨文档处理不好。比如多跳推理的”A公司创始人毕业于哪所大学“，传统RAG只能找到”A公司创始人是张三“和”张三毕业于B大学“，这两个文档相互孤立，缺乏对内容的理解。

GraphRAG会在检索和生成的过程中引入知识图谱，将信息组织成实体和关系。这样，GraphRAG能够找到`A公司 ->创始人-> 张三-> 毕业于-> B大学`的关系，实现逻辑推理。

# 11. Agent RAG

RAG和GraphRAG的回答过程都是先获取用户的查询，对查询进行增强，然后检索、拼接到提示词，再输入LLM。

如果引入了Agent，那么Agent可以根据自身能力，先看当前的查询是否需要使用RAG，如果不需要就直接回答，需要就调用RAG工具进行检索。并且可以让Agent自主决定使用的检索关键字，让它自行改写，提高召回率。

# 12. RAG问题排查

如果RAG回答不好，需要考虑三个问题。

1. 没检索到。这样可能是嵌入模型不好（更换Embedding），或者分块出现问题（分块算法），或者查询与文档不一致（查询改写），或者向量检索不佳（混合检索）。
2. 找到了但排名靠后（使用Rerank）。
3. 找到了但模型没用（上下文太长、Prompt没约束、模型能力不足）。

# 13. 做了什么RAG项目

我项目里写的运动健康管理平台中使用RAG让Agent拥有专业知识，能够提高Agent输出的专业性和准确性。每个Agent都单独设置了知识库，能够提高检索效率和专业性。如力量相关的存储运动生物力学、神经肌肉生理学等，体能相关的存储热适应性生理学、运动生理学等，饮食相关的存储运动营养学、能量平衡等知识。这样，这些Agent就能根据规划Agent给出的目标来检索相关知识，定制训练和饮食计划。

我这里对RAG的目标是召回率要90%以上，准确率需要达到85%以上。我数据库用的Chroma，Embedding用的是bge-large-zh-v1.5，LLM用的deepseek-v4-flash，框架用的LangGraph。在用户提问后，规划Agent会给力量和体能Agent给出训练目标，Agent能够自主决定是否需要调用RAG查找知识。如知道用户的身体数据，每天需要跑多少米，Agent可以查询RAG来获取相应的生理学知识来计算。最终就能够生成专业的计划。

最后，召回率达到85左右，由于分库了，对应agent的库保存的属于特定的专业知识，所以准确率也达到90%左右。

# 14. 使用什么数据库，为什么

用的是本地的Chroma。如果用其他的数据库要么太复杂，要么要钱。如Milvus需要K8s，Pinecone是云服务，但需要钱。而Chroma很简单，在本地调用chroma类就可以了。

# 15. 最大的难点

长文本检索困难，也是召回偏差。我项目中的饮食agent会得到训练计划后，就会将训练计划生成检索关键字，然后到RAG中进行检索。但是检索的质量与这里的关键字有关。如果计划大部分都是力量有氧相关，那么检索的时候，可能和力量有关的饮食知识被检索出来且有很高分数，而体能相关的只有少部分，导致排名靠后，考虑不到体能相关的饮食。

由于饮食agent接收关于力量和体能两方面的知识，不能靠一次检索查询所有知识，所以我就使用并行检索，每个关键字都独立发起一次检索，将每个关键字的前5个分块检索出来，使用重排序，与当前的计划匹配度进行打分，这样就能够返回适当的文档。

或者我也想过可以使用HyDE实现，让LLM先自己回答这里的饮食计划，由于LLM能够恰当地规划饮食，所以能够很好地检索和力量、体能相关的文档。

# 16. 新产品上线没有数据怎么办

如果没有数据，可以使用开源的数据集，一些公开的QA数据集之类，或者使用LLM来生成合成的数据集。

# 17. 向量数据库的索引

向量数据库需要将查找出数据库中与查询最相关的文档，就需要一种检索方法。

1. Flat。这是暴力搜索，遍历数据库所有向量并计算相似度。精度最高，但性能非常差。
2. IVF。对数据库的向量先进行聚类，查询时值搜索与查询最相近的几个类。
3. IVF-PQ。将高维向量压缩成更短的编码来存储，能够减少内存，计算相似度的速度也更快，但有一定的精度损失。
4. HNSW。层次导航小世界，构建一个多层图结构，一个上层节点代表多个下层节点，最底层包含所有数据。查找时需要从最上层查找最相似的节点，到下一层继续寻找最相似的节点，以此类推。精度高，速度快，但需要大量内存。

# 18. 混合检索

由于对文档的要求不同，有的需要语义相似，如句子，有的需要完全匹配，如姓名，ID等。因此，单纯的向量检索和关键词检索不够，需要使用混合检索。混合检索包含了向量检索和关键词检索。

混合检索分别检索到了文档，并且有两类分数后，需要进行融合，得到最终的排名。

1. 固定权重融合。分别对分数进行归一化，按照固定比例进行加权求和。
2. 排名融合RRF。基于文档在不同结果中的排名计算分数。
3. 模型重排。用专门的交叉编码器或LLM对候选文档进行计算。

# 19. 为什么需要两阶段检索，包含向量检索+Rerank

向量检索中是用的是双编码器，查询和文档独立编码成向量。这种设计是文档向量可以离线计算，查询时只需要看查询与文档的相似度即可。这能够节省很多时间，但丢失了一些细粒度的信息。

Rerank使用交叉编码器，能够将查询和文档拼接在一起送入模型，这样能够捕获细微语义上的差异，排序准确，但需要实时计算，开销大。

所以需要先通过向量检索得到少部分可能相关的文档，然后再使用交叉编码器来进行细粒度的计算。

# 20. HNSW怎么调参

HNSW的参数有三个。

M表示最大连接数，图中每个节点允许的连接数。如果提升，那么每个节点能够连接下层更多节点，召回率提升，但检索速度会下降。

ef_construction表示新节点加入时，会连接多少个邻居。如果提升，索引质量更好，但构建速度会降低。

ml表示层级衰减因子，控制高层节点的稀疏程度。ml越小，高层节点越小，可能导致高层节点无法完全表示低层的连接节点。

ef_search表示检索时查找的节点数。

top_k表示最终返回的结果数。

一般M取16，ef_construction取200，ef_search取100。

# 21. 什么是DiskANN

在HNSW中，由于需要保存大量节点，导致需要占用大量内存。因此DiskANN将索引放到了磁盘中，只在内存保留图索引的元数据、经过PQ的向量。这样就可以处理超多数据，且达到非常高的召回率。
