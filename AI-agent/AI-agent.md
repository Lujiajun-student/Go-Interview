# 1. Agent和大模型的区别是什么

普通的大模型本质是一个生成式大模型，给定输入，它会预测接下来的输出。而chat版本的就是给定一个问题，它会给出回答。但这种是被动的，它只会给出输出，不能做事情，而且知识是固定的，不通过训练或者RAG，知识就不会更新。

而Agent包含了更多的功能。Agent = 大模型 + 规划 + 记忆 + 工具。Agent能够将复杂的任务进行拆解，比如我要访问什么网站，我要怎么组织内容，我要使用什么工具之类。

这里需要

比如使用工具，需要通过提示词告诉大模型工具怎么使用，也就是应该返回什么样的结构数据，这样根据这里的返回数据，能够获取需要执行的方法以及参数，然后执行这个方法，将结果返回给大模型，大模型就获取到需要的结果。这样，大模型实现了工具调用。

而记忆的话，需要设计短期记忆和长期记忆。短期记忆可以存在上下文发送给大模型，长期记忆的化，需要用向量数据库来存储，需要的时候通过语义检索获取。

还有规划。这需要实现多步推理和自我纠错。复杂任务很难一步达成，需要将问题分为多个步骤。假如Agent在执行某一步时出错了，它需要能够检测到失败并分析原因，换一种方式来重试。

# 2. Agent的基本架构

有大脑、规划、记忆和工具使用四个。

大脑就是大模型本身，给定写好的系统提示词，大模型就能分析用户输入，判断下一步应该做什么，是需要规划，调用工具，寻找知识，还是可以结束。而其他三个部件使用后，都需要将结果告知给大模型。

规划就是用一个模型，将复杂任务拆解为多个子任务。比如帮我查找一篇论文，并写出示例代码，就需要有检索资料、分析知识、编写脚本等任务。在这个过程中，agent需要根据自己的历史行为来指出错误并进行优化。这可以使用ReAct或者Reflexion。这个规划过程依赖模型的推理能力，有两种方法能够提升推理能力。

1. CoT思维链。在提示词中要求模型给出最终答案之前，需要先输出中间的推理过程。这样，大模型的输出就会呈现从A到B，再到C，然后输出结果。思维链能够提升大模型处理复杂任务的准确率。但如果其中一步推导错了，接下来就会越来越离谱。
2. ToT思维树。它认为复杂问题的单一推理是不够的，需要产生多个推理方案，寻找最优的方法来继续推理。步骤为：在当前状态下生成多个可能的下一步，评价每个下一步对最终目标的价值，然后寻找最优路径，根据最优路径来进行推理。

现在的规划主要有两种模式，一是先规划后执行，让LLM输出完整的步骤，然后按顺序执行。二是边执行边规划，每走一步就思考下一步应该干什么。

记忆分为长期记忆和短期记忆，短期记忆能够放到上下文，长期记忆就放到向量数据库，有需求的时候就检索。

短期记忆最大的问题是上下文有限，如果对话过多，需要把前面的上下文做摘要浓缩，或者做滑动窗口。

长期记忆最主要是选择什么应该存，什么不应该存，以及存了之后怎么管理。最好的方法是在存储的时候做重要性评估，只持久化重要的信息。

而工具是用来告诉模型工具叫什么名字，能做什么事，需要什么参数。交给agent后，agent决定调用时，就会从工具中选择工具，把决策通过json的格式给出来，交给其他函数执行，结果再反馈给模型。

这样的话，agent就会运行成下面的伪代码过程。

```python
def agent_run(user_goal: str):
    # 规划模块，将目标拆成步骤列表
    plan = llm.plan(user_goal)
    memory = [] # 短期记忆
    for step in plan:
        # 做决策
        action = llm.decide(
        step=step,
        history=memory,
        long_term=vector_db.search(step)
        )
        if action.type == "tool_call":
            result = tools.execute(action.tool_name, action.args)
            memory.append({"step": step, "result": result}) # 执行结果存入记忆
        elif action.type == "final_answer":
            # 执行结束，最终返回
            return action.content
```

# 3. Tool

Tools是一个工具，需要给大模型看，大模型就能知道它能够调用哪些工具。这个tools给出能够调用的方法、描述、输入和输出规范。

```python
tools = [
    {
        "name": "web_search",
        "description": "在互联网上搜索信息，适合查询实时数据",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "搜索关键字"}
            },
            "required": ["query"]
        }
    },
    {
        "name": "send_email",
        "description": "向指定邮箱发送邮件",
        "parameters": {
            "type": "object",
            "properties": {
                "to": {"type": "string", "description": "收件人邮箱地址"},
                "subject": {"type": "string", "description": "邮箱主题"},
                "body": {"type": "string", "description": "邮箱正文"}
            },
            "required": ["to", "subject", "body"]
        }
    }
]
```

上面就是定义了工具，里面写了大模型能够调用的方法。如果模型返回的是send_email，那么后端截获了请求后，就要调用这个方法，根据properties里的内容来发送邮件。

# 4. Agent

Agent就是有了工具，需要决定使用什么工具的角色。

比如给Agent一个目标，帮我查询最近的天气，那么agent根据工具，会返回一个关于web_search的json文件，然后后端获取这个请求，执行了搜索方法，将搜索结果添加到当前状态，agent再做下一步决策。这里agent和工具方法可以构建成有向图，agent指向所有工具方法，所有方法又指向agent，这样agent就能根据需求来调用所有工具。

但调用不能无限调用，除了agent认为任务完成，给出结束工作流的情况，还需要加多停止机制。

1. 最大循环次数。
2. 计算token累积。
3. 限制执行时间。

还有，Agent有另一个副作用，行为是随机性的。每次调用的推理过程都不一样，最终结果可能也会不一样。在调用方法后，使用日志记录agent的思考过程和工具调用结果。

# 5. Workflow

工作流是用来定义复杂任务执行的步骤。将整个执行流程写到代码里，大模型、agent和工具都只是其中一个节点，每个节点完成自己的那一步，接下来要去哪里，就要根据定义好的工作流来决定。

工作流主要有三个元素。

1. 节点。节点是一个具体动作，比如调用一次大模型，运行一个工具类等。
2. 边。定义去哪里。完成一个节点后，就会调用节点后接下来的节点。边可以是条件性的，也可以说确定性的。
3. 状态。状态由多个节点之间共享，A节点产生的信息存入状态，B节点从状态中读取信息。

# 6. Agent的形式

1. ReAct。LLM推理的时候有三个步骤，`Thought -> Action -> Observation`。首先思考当前的任务，然后给出行动，拿到行动的结果后观察是否符合预期，再思考接下来应该怎么做。这个方法属于走一步看一步，拿到的是局部最优，最终可能会偏离原来的任务。
2. Plan-and-Execute。把规划和执行分开，让一个LLM做规划，另一个LLM来执行。首先LLM把复杂问题拆解成子任务，其他LLM把这些子任务逐个完成，将结果返回给规划的LLM来查看，是否完成任务。在这里如果一个步骤完成的不好，那么规划的LLM可能会修改接下来的步骤。这样，就有一个LLM保持整体状态，保证最终的结果不会偏离原来的任务。
3. Reflexion。引入了自评机制，模型先给出一个方案，让另一个Agent对方案进行批判，返回意见，根据返回方案进行修改，直到达到规定的质量水平。

怎么选？

ReAct适合用于简单的任务，Plan-and-Execute适合复杂的任务，能够将复杂任务拆解成多个小任务来简化，Reflection适合对输出准确度要求高的或者严谨的，可以反复自我检查来提高质量。

# 7. 推理模式

推理模式主要有思维链CoT、思维树ToT、ReAct等。

思维链就是让大模型先分析当前的情况，将推理的过程写出来，然后再给出答案。这样的话，写出来的推理内容就会进入上下文，后续生成的内容会紧贴推理内容。CoT有两种触发方式，第一种是`Zero-shot CoT`，在提示词末尾添加`让我们一步步思考`即可。第二种是`Few-shot CoT`，给出几个带有推理过程的实例，让LLM根据这些推理过程来模仿。

还有思维树ToT，针对当前的任务，会给出多个可能的下一步，LLM会选择最优的下一步来执行。

其中思维链能做的，就是添加了推理过程，让回答内容符合推理内容，而不能有行为。因此，在CoT的推理链里添加行动，按照`思考->行动->观察`的方式来推进任务，先思考当前应该怎么做，然后调用工具来获取信息，观察工具返回的结果，然后进入下一轮的思考。

上面是单一路径的思考方式。

ReAct让LLM按照思考、行动、观察。收到任务后，首先思考当前怎么做，然后调用工具获取信息，观察信息后再思考。

Plan-and-Execute就是获取任务后，首先规划出执行步骤，然后依次完成这些子任务。如果任务失败，就重新规划。

Reflection先给出方案，然后对方案进行评判返回意见，根据意见进行修改，直到达到规定水平。

# 8. 复杂任务

复杂任务需要进行拆分。如果不拆分的话，处理任务LLM会获取大量信息，可能导致大模型没有注意到关键细节，或者搜索的信息过多导致信息量超出上下文，导致出错。因此需要对复杂任务进行拆分，让多个agent处理小的子任务，这样模型能够更专注于自己更应该做的事情。而且一旦某一个子任务出错了，只需要重新执行这个子任务即可，不需要执行整个任务。

任务拆分主要有两个，第一个是静态拆分，提前把任务流程写好，固定一个确定的工作流，每一步做什么任务，按什么顺序执行等。

第二个是动态拆分，也就是Plan-and-Execute，让大模型拆分任务，准备好工具，让LLM自行调用。

# 9. 记忆机制

Agent如果没有记忆的话，完成一次任务，后，再次调用Agent，就会丢失上一次的记忆。因此需要将Agent的记忆保留下来，这样就能让Agent保持长期的行为一致性。

记忆主要有四种类型。

1. 感知记忆。是Agent获取到的当前信息。比如用户发来的信息，传入的文档等。
2. 短期记忆。通过上下文来让模型记住之前发生的事情。包含用户的输入、模型的输出、工具调用的结果等。在一次任务，或者一个会话内会记忆，但新开窗口就会丢失。
3. 长期记忆。使用向量数据库或者日志文件等保存。在用户输入时通过检索来加载到短期记忆中。
4. 实体记忆。将用户输入中的关键信息提取出来保存。

一个记忆模块通常包含存储、检索、更新、遗忘四个部分。

1. 存储。存储层需要使用多种数据库来保存。比如历史对话，文档等通过向量数据库来保存，可以用语义相似度来检索。还有确定的事实可以用结构化存储的方式来保存。例如身高、生日等不能错的信息。还有图结构，如果实体之间存在复杂的关系，可以用图结构来保存，在推理的时候就能更好地推理。
2. 检索。Agent需要通过语义检索，并用重要性分数来确定当前记忆是否重要，还要获取信息的事件，避免使用过期的消息。
3. 更新。短期记忆可能过多，导致新的记忆无法存下。因此可以使用淘汰策略。例如递归总结，对旧段落进行摘要提取，保留关键信息腾出空间，或者使用滑动窗口，抛弃更早的记忆。
4. 遗忘。如果记忆非重要，可以设置过期时间，或者发现先前的记忆出现错误，就要删除。

记忆模块需要考虑三件事：记忆存什么，怎么存，什么时候用。

最主要存储的信息是用户的偏好、习惯等，以及任务得出的关键结论、外部知识等，像推理过程，工具返回的原始数据之类就不需要存。

存储时需要根据信息的类型来存储。像知识、对话摘要等非结构化文本可以存入向量数据库，而项目配置、个人信息等结构化信息可以通过关系型数据库或者键值对来存储。

什么时候使用记忆有两种方法。

第一种是主动检索。任务开始前，用当前任务的描述去检索记忆，将结果注入提示词，这样Agent就会带着记忆开始任务。第二种是被动检索，LLM执行任务时发现需要某种信息，就会调用工具来检索记忆。

## 9.1 短期记忆不够用

短期记忆不够，主要有三种方法。

1. 滑动窗口。只保留最新的记忆，超出上下文范围的旧信息丢弃。
2. 摘要压缩。将上下文做摘要，替换掉冗长的历史记录。
3. 将重要的信息保存到长期记忆中。
4. Mem0。是一种记忆框架，可以调用方法保存记忆和查询记忆。

# 10. single-agent和multi-agent

单智能体适合任务简单的场景，实现简单。而multi-agent适合任务量大，或者涉及多个领域的复杂场景。

multi-agent主要有两种结构，有orchestrator和Peer-to-Peer两种模式。orchestrator有一个agent统一调度其他agent，而Peer-to-Peer则是多个agent之间能够相互通信协调来解决问题。

# 11. LangChain和LangGraph的区别

LangChain是一种线性流程。接受输入，将输入模板化，调用模型，最后解析输出。

而LangGraph是一种循环图的流程。Agent思考后，可以选择调用其他工具或者Agent，然后考虑搜索到的结果是否足够，不足就继续调用，足够就停止，返回输出。

# 12. LLM规划能力

给LLM添加规划能力，可以有CoT，添加“请一步步思考“的提示词，能够让模型输出思考过程。但这种方式最大的问题是其中一步一旦出错，后面就会步步错。因此出现了ToT，让模型给出多个可能的下一步，选择最优的下一步来走。但问题是多个节点只有父子关系，兄弟节点没有联系。然后是GoT，分别独立思考多个方向，最后将多个方向得到的推理结果合并到一起来进行分析，将多个节点的信息合并在一起来进行分析。

# 13. Reflection

流程是生成、评估、改进。

首先一个agent提出任务解决方案，然后让另一个agent来评估方案。如果有问题，就提出改进，没问题就执行。

```bash
任务：{task}

当前输出：
{current_output}

请评估以上输出：
1. 有没有事实错误或逻辑问题？
2. 有没有遗漏重要内容？
3. 表达是否清晰准确？

如果输出已经足够好，回复「PASS」；
否则指出具体问题并给出改进建议。
```

需要根据任务的类型来给出具体的检查方向。

这里的反思可以在每一步后反思，或者在任务执行完后反思。每一步反思能够做得更准，但调用次数很多；任务执行完反思节省调用次数，但一旦发现错误，难以改正。

# 14. 多Agent的协作和动态切换

协作就是一个agent执行任务后，将结果传输给下一个agent来执行，并且将自己的状态共享出去，所有的agent都能看到这个状态。

动态切换靠规划者agent来做。orchestrator规划后，能够自主选择调用哪一个agent来执行任务。或者使用流水线模式，固定好工作流，一个agent执行完后到下一个agent执行，直到工作流结束。

# 15. Skill和Tool的区别

## 15.1 Tool

Tool是底层的能力接口。例如`search(query)`，即工具方法，不负责怎么做，负责做一件具体的事。模型只会决定用不用，传什么参数。

## 15.2 Skill

Skill用于教会Agent怎么完成任务，主要是写一个任务流程。在SKILL.md文件中定义技能的名称、版本、描述等，Agent能够查看文档，按需调用工具。

## 16. MCP

MCP让Agent能够用标准化的方式访问外部资源。包含工具、数据、文件、数据库、浏览器等资源。将工具等资源封装为MCPTools，那么agent就能够自动识别这些工具，并以方法注解为描述，查看方法描述、输入和输出，来自主决定是否调用该方法。

# 16. AI Agent面试总结

Agent是以大模型为核心，对目标进行感知、推理、规划、调用工具、观察结果、调整策略，并最终完成任务的系统。

LLM偏向于回答问题，而Agent强调完成任务。Agent=LLM+规划+记忆+工具。

Agent的运行如下。

```
用户目标->理解任务->制定计划->选择工具->执行动作->观察结果->更新状态->判断是否完成->输出结果
```

这也是ReAct的核心，模型会思考、执行、观察，循环往复直到满意为止。

1. 模型层

模型决定Agent的能力。

小模型适合分类、路由，简单快捷，但不适合复杂任务。

开源大模型适合本地部署，可私人定制，但推理和调用工具较复杂。

闭源大模型适合复杂推理，推理能力强，工具调用稳定，但成本高，且需要注意数据安全。

多模态大模型适合图像视频理解，能够处理视觉输入，但成本较大。

2. 指令层

Prompt在Agent中属于行为规范。

```
角色：是什么Agent
目标：完成什么任务
约束：不能做什么
工具说明：有什么工具，什么时候用，怎么用
输出格式：需要返回什么结构
停止条件：什么时候结束
错误处理：工具失败怎么重试
安全规则：什么情况下需要人工审批
```

系统提示词用来规范Agent的行为，让它只做应该做的事情。

3. 工具层

工具调用是Agent和LLM的最大区别之一。Tool Calling是一个多步的流程，给模型提供工具定义，模型返回工具调用，后端执行代码，将结果返回给模型，模型生成最终回答或者继续调用。

工具有多种工具，如执行工具、查询工具、计算工具、浏览器工具、文件工具、MCP工具等。

不好的工具是没有注释只写逻辑。

```python
def do_something(input: str):
    ...
```

好的工具需要表明工具的作用、输入输出。

```python
def search_order(order_id: str) -> dict:
    """
    根据订单 ID 查询订单详情。
    仅用于用户已经提供明确 order_id 的情况。
    返回字段包括：订单状态、支付金额、物流状态、是否可退款。
    """
```

4. 状态层

Agent需要维护状态，用来存储记忆和工具调用的结果，否则无法完成多轮思考。

```
用户目标
当前计划
已完成步骤
工具调用历史
中间结果
错误信息
是否需要人工确认
最终输出
```

如果状态管理较差，Agent会忘掉之前做了什么，也有可能重复调用一个工具，无法从失败中恢复等。

LangGraph能够用于复杂Agent，就是因为状态维护好，多步后Agent能够了解之前做了什么。

5. 记忆层

Agent的记忆分为短期记忆、会话记忆、长期记忆、外部记忆。

短期记忆是当前对话，会话记忆是当前会话的聊天记录，长期记忆是跨会话保留的记忆，外部记忆是数据库、知识库保留的记忆。

记忆的实现方式有很多种。

* 保存到上下文，好处是精确，坏处是上下文容易过长。
* 摘要压缩。好处是节省上下文，缺点是丢失细节。
* 向量检索。好处是可扩展，缺点是召回率限制。
* 结构化数据库。好处是精确，坏处是需要设计schema。

Agent有多种架构模式，也就是常见的设计模式。

1. 单轮调用Agent。

```
用户问题->判断是否调用工具->返回工具结果->总结答案
```

这是最简单的Agent，适合做简单任务，但难以完成复杂任务。

2. ReAct。

```
用户问题->思考->调用工具->观察结果->思考->调用工具->观察结果-> ... -> 观察结果->输出结果
```

适合需要边思考边执行的任务，如查找技术并对比。

3. Plan and Execution。

这种模式主要包含两类或三类Agent。

```
Planner：拆解任务
Executor：执行每个任务
Verifier：检查结果
```

这种模式适合复杂长任务，如写报告、生成方案等。优点是执行步骤清晰，缺点是依赖Planner的拆解质量，如果规划出错，后面容易步步错，有时候需要重新规划。

4. Reflection。

在执行完毕后不直接返回，而是检查是否有问题。

```
执行结果->反思错误->修改计划->重新执行
```

工具调用是Agent非常重要的能力，也就是Function Calling。

将工具的名字、描述、结构化参数提供给模型，模型返回结构化请求，应用程序执行对应的工具方法。

```python
tools = [
    {
        "name": "get_weather",
        "description": "查询某个城市的天气",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名"}
            },
            "required": ["city"]
        }
    }
]
```

工具有设计原则。

* 工具职责单一，一个工具只能做一件事。
* 参数结构化，能够通过JSON格式来约束输出。
* 描述清楚，在description中描述工具的作用。
* 高风险操作审批，如发邮件、付款等操作需要进行人工确认。
* 工具调用不能无限制，需要通过超时和重试机制来防止卡死。

而MCP的tools允许服务器暴露定义好的工具，resources服务暴露文件、数据库等上下文、prompts服务提供结构化提示模板和工作流。

因为Agent具有更大的能力，因此需要进行安全规范。如Guardrails，使用其他模型对用户输入和Agent输出先进行风险评估，再决定是否能够进入下一步。常见的风险有提示词注入、恶意调用工具、泄露隐私、幻觉等。
